# 多歌词 Provider 与 AMLL 接入计划

日期：2026-09-09。状态：代码实现与自动化验收已完成；桌面/面板实机及真实曲目抽查待执行。

本文记录与用户完成设计访谈后确认的首版范围、实施方案与验收结果。
第 5 节中的接口、配置和迁移均已落地；尚未完成的人工验收单独保留在 7.4。

架构约束沿用 [DESIGN.md](DESIGN.md)：`core/` 不依赖 QtNetwork / QtDBus，
provider 与前端保持独立扩展边界，歌词通过原子整首快照传递，保留 MPRIS 脏数据回归测试。
原设计中的“首版仅网易云”是既有实现范围；实施本计划时应同步更新设计文档中的相关决策。

## 1. 目标与首版范围

增加 AMLL 歌词源，在首选源获取不到可用歌词时补缺，并让用户选择歌词来源。
默认继续优先使用网易云，不因 AMLL 有逐词时间轴而主动替换已经成功取得的首选源歌词。

首版包含：

- 全局歌词源优先顺序，后续按 SOURCE_FIXES_PLAN.md 扩展为默认 `local → netease → amll`。
- 按当前歌曲指定首选源、恢复自动、立即重新搜索。
- 首选源失败后依次尝试其余候选源。
- AMLL 元数据索引缓存、本地检索、TTML 下载与解析。
- 保存主歌词、翻译和逐词时间，前端仍按行显示。
- 区分用户首选、实际命中来源和临时回退结果。
- 保持现有 MPRIS 播放场景，预留带平台命名空间的歌曲 ID 数据结构。

后续范围：各源的具体歌曲版本候选界面、逐词高亮、背景人声与对唱的专用显示、
罗马音及多语言译文选择，以及更多在线 provider。
本次不引入运行时动态插件系统，不要求用户部署额外检索服务。

## 2. 已确认的用户行为

### 2.1 首选源与回退

全局设置定义在线源顺序；当前歌曲的手动首选覆盖全局首选，但其余源仍按全局顺序回退，
同一个源在一次搜索中只尝试一次。未配置或未编译的源不进入有效搜索链。

例如全局为 `netease → amll`：

| 当前歌曲设置 | 实际搜索顺序 |
| --- | --- |
| 自动 | 网易云 → AMLL |
| 首选网易云 | 网易云 → AMLL |
| 首选 AMLL | AMLL → 网易云 |

“指定源”表示指定首选源，并非只允许查询该源。
搜索无结果、匹配不合格、请求失败、解析失败或取得空歌词时，继续下一个源。
仅缺少翻译不算失败；一次显示采用同一来源的完整歌词，不拼接不同源的原文和翻译。
保持现有本地手工覆盖能力：对确定的歌曲引用读取对应 override，不能把它当作普通在线候选。

### 2.2 单曲偏好

- 用户手动指定后，按现有歌曲指纹持久化该首选源，重启后仍有效。
- 临时回退只更新实际采用的歌词，不覆盖手动偏好。
- “恢复自动”删除单曲偏好，重新按全局顺序解析当前歌曲。
- 切换源、恢复自动和重新搜索都立即生效，不要求重启 daemon。
- “重新搜索”保留用户偏好，但绕过本次搜索链的旧负缓存和结果映射短路。
- 各来源的时间偏移继续按各自 `(provider, trackId)` 保存；不把旧源的偏移复制到新源。
- 多个桌面或面板实例共享偏好，必须看到一致的实际来源和搜索结果。

首版按现有指纹识别单曲，不承诺不同播放器或不同音频文件之间自动共享偏好。

### 2.3 已有缓存与首选源重试

正常播放先显示已经可用的歌词缓存。若缓存来自回退源，则在下次播放该曲、
且首选源的失败冷却已结束时，后台重新尝试首选源；成功后原子替换整首歌词。
首选源再次失败时继续显示已有可用结果，不因重试而清空屏幕。

同一播放过程不因冷却到期反复发起重试。暂停/恢复、普通进度更新、拖动进度均不应成为重试循环。
实际重新进入该曲或检测到新的播放轮次时，才按策略判断；仍须保留现有拖动与单曲循环对轴逻辑。
用户明确触发的换源或重新搜索立即尝试，不等待冷却。

若最终所有源均失败且没有可用缓存，沿现有歌词状态契约报告无结果或网络错误，
日志保留每个源的具体失败原因，不用最后一次失败掩盖整个搜索过程。

### 2.4 AMLL 的版本匹配

AMLL 匹配保留查询、主标题和别名中的版本后缀；网易云现有标题清理行为保持不变。
可以继续规范化大小写、全半角、标点和空白，但不能在 AMLL 路径中删除 Live、Remix、
Cover、重制版等版本信息。

| 版本证据 | 处理 |
| --- | --- |
| 双方版本一致，或双方均没有版本标记 | 正常候选 |
| 只有一方带版本标记 | 允许匹配，但属于 AMLL 的最低优先级候选 |
| 双方明确标注不同版本 | 排除候选 |

最低优先级不是简单扣少量分数：所有合格的正常候选都应排在它之前。
只有没有可用的正常候选时才考虑它，且仍须通过歌名、歌手等基础匹配门槛。
该分层发生在 AMLL 内部，不改变全局 provider 回退顺序。
专辑证据仍参与匹配；缺少时长时保持“未知”，不把最后一句歌词结束时间当成歌曲总时长。

## 3. 上游调查结论

AMLL 适合作为可选的补充源。它是社区歌词库，不能假定涵盖用户所有曲目；
实际命中收益需用常听曲目验证。

2026-09-09 调查时取得的数据：

- `metadata/raw-lyrics-index.jsonl` 约 1.60 MB，包含 3,275 条历史投稿记录，不能等同于独立歌曲数。
- 对应 `raw-lyrics/version.json` 的构建日期为 2026-09-06；这些数字是本次快照事实，不是运行时常量。
- 支持网易云、QQ、Apple Music、Spotify 的平台歌曲 ID；无需依赖网易云搜索先成功才能查询 AMLL。
- 索引没有统一的歌曲总时长字段，原始索引包含历史修订，需去重并处理更新。
- 本次网易云目录有 3,533 份 TTML，LRC/YRC 各 3,356 份；实测存在 TTML 返回 200、
  对应 LRC/YRC 返回 404 的记录，因此接入以 TTML 为主。
- 上游主要对有效网易云 ID 对应音源保证时间轴质量，不能假设跨平台或不同录音版本完全同步。

## 5. 技术实施方案

以下是落实已确认行为的工程方案。接口名称、具体 schema 和刷新间隔可在实现中调整，
但不能改变第 2 节的用户行为。

### 5.1 查询、引用与匹配策略

1. 为查询预留可选的平台歌曲 ID 集合，ID 必须带平台命名空间；本次不依赖其有值。
   不把 `mpris:trackid` 当作音乐平台 ID，不改变已有指纹与来源平台判定。
2. 将“标题是否保留版本”和候选版本分层作为显式匹配策略，避免修改公共清理函数后影响网易云。
3. AMLL 索引中同一作品可能存在多个平台关联和历史修订。检索前去除重复关联，
   按上游元数据与生成规则确定当前版本，不把历史文件逐个当成独立的同等候选。
4. 区分稳定歌曲引用和具体歌词文件版本。优先以带命名空间的平台 ID 作为稳定引用，
   原始 TTML 文件名作为内容版本定位；索引更新应保留既有绑定，避免普通修订导致偏移丢失。
5. 诊断输出记录来源、版本候选层级、评分、被拒原因和最终选择。
   同一份诊断必须复用实际决策路径，不能展示另一套评分结果。

### 5.2 AMLL 索引与获取

- 新增 `providers/amll/`，网络及索引更新全部留在 provider 层；通过独立 CMake option 编译。
- 下载并缓存原始元数据索引，在本地以标题、歌手、专辑与别名检索，然后按需获取 TTML。
- 不要求克隆整个仓库，不扫描远端目录来完成每次搜索，不把第三方搜索站作为必需依赖。
- 建议默认使用 GitHub Raw；地址与超时通过 provider 配置暴露，镜像可配置，不自动轮询任意社区镜像。
- 索引优先使用已有有效缓存，过期后异步刷新；可从每日刷新作为初始实现默认值，
  并采用服务端支持的条件请求。首次无缓存时才等待首次索引下载。
- 新索引校验通过后原子替换，失败继续使用旧索引；设置合理的体积、响应时间和解析上限。
- 并发查询共享一次索引更新，避免多实例或快速换曲重复下载。
- 下载 TTML 时明确区分 HTTP、网络传输、格式错误和没有歌词，沿用现有有限重试语义。

### 5.3 TTML 解析与首版降级

- 在 `core/lyric/` 使用 QtCore 可用的 XML 解析能力，实现命名空间感知的 TTML parser。
- 支持 AMLL 使用的秒、分秒、时分秒时间格式，保留行及词的开始/结束时间和词间空格。
- 兼容行内翻译和头部关联翻译；先映射到现有每行一份翻译，处理重复译文。
  多译文情况下采用确定的语言优先规则并以 fixture 固定，不依赖 XML 节点偶然顺序。
- 不把翻译、罗马音、元数据或背景人声拼入主歌词。首版以主声部逐行显示，
  不新增背景人声/对唱专用布局；重叠行按既有时间线能力作确定处理并记录限制。
- 不支持的附加语义不应破坏可用主歌词；非法 XML、无有效主歌词和不可用时间轴须明确返回失败。
- 保存作者、来源和原始版本定位所需的元数据，为追踪修订及后续扩展提供依据。
- 不修改前端为逐字计时，不引入 AMLL 渲染库；全文仍以原子快照交付。

### 5.4 持久化与缓存迁移

必须分开保存三类状态：用户单曲首选、当前实际结果、各 provider 的查询失败记录。
不能继续用一条指纹映射同时表达“用户选择”与“上次命中”。

- 单曲首选按现有指纹保存；实际歌词正文及偏移继续使用 `(provider, trackId)`。
- 按 provider 保存匹配映射及失败冷却，保证首选失败不抑制其他源。
  非音乐过滤仍是解析前的独立判断，不能因拆分负缓存而失效。
- 旧全局 miss 没有足够信息证明 AMLL 已经尝试过，迁移后不能据此抑制新增源。
- 旧有效正文、offset、手工覆盖与指纹映射保留；旧映射不能自动变成用户手动首选。
- 保留现有网络失败 5 分钟、无候选 7 天的冷却基线；源配置或索引版本变化后，
  使相关的过时 miss 可重新评估，避免新数据被长期旧失败记录挡住。
- 手动换源与重搜绕过旧命中的直接返回，但可继续显示旧歌词，直到新结果成功。
- 迁移应事务化且可重复执行；记录持久化失败，不能把未落库的用户偏好报告为保存成功。

### 5.5 后台编排与控制入口

Resolver 保持异步执行，并将“一次解析”绑定到歌曲指纹和请求世代。
换曲、播放器消失、用户改源或再次重搜后，旧结果不得更新当前显示、绑定或偏好。
歌词缓存可先发布，后续成功结果仍一次性发布整首文档，不混合来源或逐行追加。

当前没有即时重搜 IPC。建议在 daemon 提供小型会话 D-Bus 控制接口，
用于设置/清除当前歌曲首选及请求重搜；由 daemon 统一更新偏好与启动解析。
命令带预期歌曲指纹，必要时加快照序号，避免用户打开菜单后换歌导致操作错歌。
前端异步报告命令失败，不把读取 `state.json` 的 `reload()` 冒充网络重搜。

控制通道只承担用户命令；歌词、锚点和实际结果仍通过既有快照读取。
快照仅增加兼容字段表达首选与实际来源，保留旧前端可读取的全文、时间锚点及 `seq` 语义。

### 5.6 设置与界面

- 全局优先级与 AMLL 网络配置放到现有服务设置页，明确所有部件实例共享。
  可沿用现有保存/重启路径；单曲操作使用即时控制接口。
- 当前曲的选源、恢复自动、重新搜索放到已有右键菜单，桌面和面板共用。
- 菜单区分“首选 AMLL”和“当前实际使用网易云”等状态，临时回退不改变首选勾选项。
- 没有当前歌曲或服务不可用时禁用相关操作；失败反馈可见，不清空可用歌词。
- 所有新增文案进入现有翻译流程，不在桌面歌词区域新增播放控制或诊断面板。

## 6. 实施顺序

1. **匹配与数据契约**：版本策略、候选分层、可选平台 ID、稳定歌曲引用及对应测试。
2. **TTML 解析**：主歌词/译文/词时间到现有模型的转换，完成解析与存储往返测试。
3. **AMLL Provider**：索引读取、去重、异步更新、检索和 TTML 获取，接入编译开关。
4. **状态与迁移**：单曲偏好、按源结果映射、失败冷却、旧缓存迁移。
5. **Resolver**：按偏好回退、空结果继续、缓存先显示、受控重试与旧请求隔离。
6. **控制接口与前端**：即时单曲操作、全局配置、多实例同步、实际来源反馈。
7. **集成验收与文档**：诊断输出、真实场景验证，更新 DESIGN、README 和未发布变更说明。

每步保持可构建并完成相关测试；纯解析、匹配与 provider 测试不依赖真实外网。
完成全部步骤后再将本计划标记为已实现。

## 7. 验收标准

### 7.1 用户行为

- [x] 默认网易云成功时不查询 AMLL；网易云失败时可从 AMLL 取得并显示歌词。
- [x] 首选 AMLL 失败时可回退网易云，但当前曲首选仍为 AMLL，重启后不丢失。
- [x] 恢复自动立即按全局顺序重搜；修改全局顺序不覆盖已有单曲偏好。
- [x] 主动重搜不被旧正文映射或负缓存短路。
- [x] 缓存歌词能先显示；下次播放且冷却结束后重试首选源，失败不清空缓存显示。
- [x] 同一播放过程中不会因进度事件、暂停恢复或冷却到期反复请求并切换源。
- [x] 各源偏移独立，临时回退和恢复首选均不会串用偏移。

### 7.2 匹配与解析

- [x] AMLL 查询、主标题、别名都保留版本后缀；网易云既有匹配用例结果不变。
- [x] 正常候选优先于所有单边后缀候选；后者仍必须通过基础匹配门槛。
- [x] 双方明确版本冲突被排除；缺时长不会伪造时长或触发依赖时长的兜底。
